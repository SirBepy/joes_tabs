# Supabase (joes_tabs backend)

Postgres schema + local dev for the tabs app. Everything here runs locally against
the Supabase Docker stack. A hosted/cloud project is NOT required to build or test.

## Layout

- `config.toml` - local stack config (generated by `supabase init`).
- `migrations/0001_init.sql` - initial schema: `instruments`, `songs`, `tabs`,
  the `tab_source` / `tab_status` enums, full-text search, RLS policies, and the
  `search_songs(query text)` RPC.

## Prerequisites

- Docker Desktop running.
- Supabase CLI (`supabase --version`; built/tested with v2.78.1).

## Local dev

Start the full local stack (Postgres, Auth, REST, Studio). First run pulls images
and can take several minutes:

```powershell
supabase start
```

Apply / re-apply all migrations from scratch against the local DB:

```powershell
supabase db reset
```

`db reset` drops the local database, re-runs every file in `migrations/` in order,
then runs any seed. Use it whenever you change a migration.

Stop the stack when done (frees Docker resources):

```powershell
supabase stop
```

`supabase start` prints the local URLs and keys you need:

- `API URL` -> `SUPABASE_URL` (typically `http://127.0.0.1:54321`)
- `anon key` -> `SUPABASE_ANON_KEY`
- `service_role key` -> seeding/admin ONLY (see below)
- Studio UI is on its own port for inspecting tables and running SQL.

## App env wiring (Flutter)

The app reads its connection config from `--dart-define` (never committed). Local
example:

```powershell
flutter run `
  --dart-define=SUPABASE_URL=http://127.0.0.1:54321 `
  --dart-define=SUPABASE_ANON_KEY=<anon key from `supabase start`>
```

For a hosted project later, swap in the cloud project's URL + anon key. Keep keys
in an untracked `.env` / pass via `--dart-define`; never hardcode them in source.

## Security model (v1)

Row Level Security is enabled on `instruments`, `songs`, and `tabs`. The public
(`anon`) role is read-only and scoped:

- `instruments` - publicly readable (reference data).
- `tabs` - only rows with `status = 'published'` are selectable.
- `songs` - selectable only if they have at least one published tab.
- No public `insert` / `update` / `delete` on any table.

### service_role key (seeding only)

The `service_role` key bypasses RLS. It is used ONLY by the seed script / admin
tooling to load songs and tabs. It must NEVER be embedded in the Flutter app or
shipped to clients - the app uses the `anon` key exclusively.

## search_songs RPC

`search_songs(query text)` runs full-text search over song title + artist using the
generated `search_tsv` column (GIN-indexed). It is `security invoker`, so RLS still
applies: anonymous callers only ever get songs that have a published tab. An empty
or whitespace query returns all visible songs (title-ordered). Call it from the app
via the Supabase RPC interface.

## Validation status

`migrations/0001_init.sql` was validated against Postgres 17 (the local stack's
major version): all DDL applied cleanly, RLS was confirmed (anon sees published
content only and cannot write), and `search_songs` was confirmed to match by title
and artist and to respect RLS.
